# Короткое исследование

## JTBD клиента

1. **Когда нужны оборотные средства**, я хочу за несколько минут понять доступную сумму и условия, чтобы не собирать документы и не ехать в отделение.
2. **Когда я подаю заявку**, я хочу видеть, на каком этапе она находится и что произойдёт дальше, чтобы не звонить и не писать с вопросами.
3. **Когда решение отрицательное**, я хочу понять человеческую причину и что можно исправить, чтобы повторная заявка была осмысленной.
4. **Когда банк просит уточнения**, я хочу ответить и загрузить документы в том же окне, не теряя контекст.
5. **Когда условия одобрены**, я хочу принять оферту и завершить сделку в одном кабинете.

## JTBD сотрудника банка

1. Быстро увидеть очередь и заявки, закреплённые лично за мной.
2. Получить проверенные реестровые, финансовые данные и прозрачный скоринг без ручного сбора.
3. Принять решение по четырём сценариям, зафиксировав комментарий и причину.
4. Не рассматривать собственную заявку и заявки, связанные с уже рассмотренной цепочкой (правило «свежего взгляда»).
5. Видеть SLA и нагрузку, чтобы не потерять заявку.

## JTBD администратора

1. Управлять доступом и ролями, не вмешиваясь в кредитные решения.
2. Наблюдать все заявки, включая очередь без назначенного сотрудника.
3. Менять продукты и параметры скоринга версионированно.
4. Проверять неизменяемый журнал аудита и целостность его цепочки.

## Границы MVP

**Входит:** сквозной путь «каталог → проверка ИНН → черновик → отправка → автоматические проверки → назначение → решение сотрудника → результат → оферта → демо-подписание и зачисление»; четыре исхода; роли и серверный RBAC; аудит; моки реестра и БКИ; центр уведомлений; адаптивный интерфейс; Docker Compose; тесты.

**Не входит:** реальные интеграции, юридически значимая ЭП, реальное кредитование, платежи, OCR, мобильное приложение, внешние каналы коммуникации, LLM, многоарендность, промышленный SSO/2FA.

## Потребность → решение в продукте

| Потребность (из ТЗ и JTBD) | Решение |
|---|---|
| Клиент не знает, какой продукт нужен | Первый шаг мастера — «на что нужны деньги», продукт подбирается по задаче |
| Одни и те же данные вводятся много раз | ИНН подтягивает реквизиты и финансы из реестра; черновик сохраняется |
| Непонятно, что с заявкой после отправки | Статус обновляется сам, таймлайн, центр уведомлений, понятная причина решения |
| Нужна информация под свой бизнес | Персональная лента новостей по ОКВЭД, форме и возрасту бизнеса, статусу заявок |
| Заявку подаёт уполномоченное лицо | Должность заявителя, подтверждение полномочий и согласия при отправке |
| Банку нужно объяснимое решение | Прозрачный скоринг отдельно от кредитной логики, решение всегда за сотрудником |
| Конфликт интересов | Разделение рабочих и клиентских учёток, связанное лицо, «свежий взгляд» с историей решений |
| Контроль и расследования | Неизменяемый аудит с цепочкой хешей и риск-исключениями |

## Критерии успеха прототипа

- Жюри запускает `docker compose up --build` на чистой машине и за 5 минут проходит все четыре исхода.
- Статусы меняются последовательно, недопустимые переходы отклоняются сервером.
- Клиент не видит чужие заявки, сотрудник — незакреплённые, администратор не может принять кредитное решение.
- Каждое значимое действие остаётся в журнале аудита, цепочка проверяема.
- Нет платных сервисов, внешних ключей и исходящих вызовов, кроме двух локальных моков.
