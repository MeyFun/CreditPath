# Тестовые сценарии

## Учётные записи

Пароль: `DemoPass123!`.

- `client1`, `client2` — клиенты.
- `employee1`, `employee2`, `employee3` — сотрудники банка.
- `admin` — администратор.

Назначение выполняется round-robin по минимальной нагрузке. В последовательном демо-прогоне заявки обычно попадают `employee1`; если очередь у него занята, откройте `employee2` или `employee3`. Точный исполнитель виден администратору в разделе «Все заявки».

## Пользовательский путь

1. Войти как `client1`.
2. Открыть «Новая заявка».
3. Выбрать продукт и цель.
4. Проверить ИНН; при успехе увидеть реестровые данные, при 404 — понятную ошибку.
5. Указать сумму, срок, обеспечение. Проверить аннуитетный платёж.
6. Приложить PDF/JPEG/PNG до 10 МБ (опционально).
7. Сохранить черновик, обновить страницу и убедиться, что данные сохранились.
8. Отправить заявку. Убедиться, что кнопка защищена Idempotency-Key.
9. Наблюдать автоматические статусы; при `NEED_INFO` ответить в решении.
10. Войти сотрудником, найти назначенную заявку, изучить реестр, БКИ и факторы.
11. Принять одно из четырёх решений; для отказа/запроса данных ввести комментарий.
12. Вернуться клиентом и увидеть итог, причину и оферту.
13. Принять оферту, выполнить демо-подписание и демо-зачисление.

## Проверка прав

| Проверка | Ожидание |
|---|---|
| `client2` открывает заявку `client1` по прямому URL API | 404, данные не раскрываются |
| `employee1` открывает заявку, назначенную `employee2` | 404 |
| `employee1` открывает собственную заявку в служебном контуре | 404, заявка отсутствует в очереди и статистике |
| `admin` вызывает эндпоинт решения сотрудника | 403 |
| `admin` пытается одобрить собственную клиентскую заявку | 403 |
| Сотрудник и администратор открывают клиентский кабинет | 200; продукты, новая заявка, «Мои заявки», профиль |
| Сотрудник одобряет заявку с баллом ниже 70, при стоп-факторе или рекомендации «Отказ» | Решение сохраняется, появляется отдельное событие `RISK_OVERRIDE` и запись `application.risk_override` в аудите |
| Сотрудник из цепочки предыдущих заявок пытается решить повторную | 403, «свежий взгляд» |
| Клиент вызывает админские эндпоинты | 403 |
| Клиент видит документ другой заявки | 404 |
| Смена роли клиент → сотрудник → клиент | Только администратор; запись в аудите |
| Попытка изменить/удалить строку аудита в PostgreSQL | Ошибка триггера, запись неизменяема |

## Проверка аудита

- Каждый переход статуса создаёт `application.status_changed`.
- Каждое решение — `application.decision`.
- Смена роли — `user.role_changed` с полями было/стало.
- Изменение продукта и скоринга — отдельные события.
- `GET /api/admin/audit/verify` возвращает `valid: true`.
- При изменении `after` записи напрямую в БД проверка возвращает `valid: false` и номер записи (проверяется pytest).

## Негативные проверки вручную

- ИНН `9900000018` — неверная контрольная сумма → 422 на форме.
- ИНН из 11 цифр → ошибка длины.
- Сумма вне диапазона продукта → ошибка до отправки.
- Заявка на оборудование без обеспечения → отказ валидации.
- Файл больше 10 МБ или неверного типа → 413/415.
- Неверный пароль 5+ раз → 429 с `Retry-After`.
- Повторная отправка с тем же Idempotency-Key → та же заявка, без дубля.
- Отказ/запрос данных без комментария → 422.
- Истёкшая оферта → 409.
- Отправка без подтверждения полномочий или согласия на запрос в БКИ → 422.
- «Другие условия» с суммой больше запрошенной или с теми же условиями → 422.
- Сотрудник открывает заявку связанного лица по прямой ссылке → 404; в его очереди её нет.
- Сотрудник или администратор открывает `/api/client/dashboard` → 403.
- `X-Forwarded-For` с новым адресом на каждой попытке не обходит лимит входа → 429.
