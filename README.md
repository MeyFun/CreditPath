# CreditPath

Демонстрационный прототип цифрового кредитного кабинета для малого и микробизнеса. Один веб-продукт, в котором предприниматель выбирает продукт, проверяет компанию по ИНН, подаёт заявку и видит её статус, а сотрудник банка обрабатывает назначенную заявку и принимает финальное решение. Администратор управляет ролями и справочниками и читает неизменяемый журнал аудита.

> Все компании, ИНН, финансовые показатели, реестр и кредитная история — синтетические. Подписание договора и зачисление средств имитируются и явно помечены в интерфейсе. Прототип не является кредитной организацией и не предлагает реальные финансовые услуги.

## Сквозной сценарий

```text
Гость → каталог / калькулятор / FAQ
Клиент → проверка ИНН → черновик → отправка
Система → VALIDATION → ENRICHMENT (registry + BKI) → SCORING → DECISION_DRAFT → IN_REVIEW
Сотрудник → одобрить / другие условия / запросить данные / отказать
Клиент → оферта → демо-подписание → демо-зачисление
Администратор → роли, справочники, все заявки, проверка цепочки аудита
```

Базовый клиентский кабинет доступен **всем авторизованным ролям**: клиент, сотрудник банка и администратор видят продукты, могут проверить ИНН, создать и отправить собственную заявку, приложить документы, принять оферту и пройти демо-подписание. При этом:

- сотрудник банка не видит собственную заявку в служебной очереди и не может открыть или одобрить её как сотрудник;
- администратор пользуется клиентским кабинетом как заявитель, но не получает доступа к панели кредитных решений;
- служебные разделы доступны только соответствующей роли: очередь и решения — сотруднику, управление ролями и аудит — администратору.

## Стек

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2, PostgreSQL 16, pytest.
- **Frontend:** React 18, TypeScript, Vite, React Router, TanStack Query, собственная CSS-дизайн-система.
- **Runtime:** nginx отдаёт SPA и проксирует `/api`, `/docs`, `/openapi.json`, локальный Swagger UI.
- **Моки:** два независимых FastAPI-сервиса `registry-mock` и `bki-mock`.
- **Инфраструктура:** Docker Compose, healthchecks, именованные тома, non-root процессы.

Архитектура: [docs/architecture.md](docs/architecture.md). Диаграмма статусов: [docs/state-diagram.md](docs/state-diagram.md). Модель данных: [docs/data-model.md](docs/data-model.md). Решения: [docs/DECISIONS.md](docs/DECISIONS.md). Карта макетов: [docs/design-map.md](docs/design-map.md).

## Быстрый запуск

Требования: Docker Engine 24+ и Docker Compose v2, свободные порты `8080` и `8000`.

```bash
docker compose up --build
```

Опционально можно заранее скопировать настройки:

```bash
cp .env.example .env
```

Без `.env` compose использует демонстрационные значения по умолчанию, поэтому команда выше запускается на чистом клоне. После старта:

| Что | Адрес |
|---|---|
| Веб-приложение | http://localhost:8080 |
| Swagger UI | http://localhost:8080/docs |
| OpenAPI JSON | http://localhost:8080/openapi.json |
| API напрямую | http://localhost:8000/api |
| Health backend | http://localhost:8000/health |

Остановка и полный сброс данных:

```bash
docker compose down
docker compose down -v   # удалить базу и загруженные файлы
```

## Демонстрационные учётные записи

Пароль всех учётных записей: **`DemoPass123!`**. На странице входа пароль подсказан и подставляется по кнопке демо-доступа.

| Логин | Роль | Что показывает |
|---|---|---|
| `client1` | Клиент | Кабинет предпринимателя, компания «Северный Ветер» |
| `client2` | Клиент | Вторая компания, «Торговый Дом Волга» |
| `employee1` | Сотрудник банка | Служебная очередь и решения + клиентский кабинет |
| `employee2` | Сотрудник банка | Альтернативный сотрудник + клиентский кабинет |
| `employee3` | Сотрудник банка | Альтернативный сотрудник + клиентский кабинет |
| `admin` | Администратор | Пользователи, аудит, справочники + клиентский кабинет без права решения |

В боковом меню сотрудника и администратора есть блок «Кабинет предпринимателя». В клиентском кабинете, наоборот, отображается блок служебного контура соответствующей роли.

## Синтетические ИНН для проверки

| ИНН | Компания | Сценарий | Ожидаемый исход |
|---|---|---|---|
| `9900000017` | ООО «Северный Ветер» | здоровая компания | Одобрено |
| `9900000024` | ООО «Гранит-Снаб» | активная просрочка | Отказ (стоп-фактор) |
| `9900000031` | ООО «Торговый Дом Волга» | сумма 8 млн при выручке 10 млн | Одобрено на других условиях (≈ 4 млн) |
| `9900000049` | ООО «Тихий Двор» | нет финансовых показателей | Нужны дополнительные данные |
| `9900000056` | ООО «Архив-Строй» | ликвидирована | Отказ (стоп-фактор) |
| `990000001246` | ИП Кузнецова М. С. | ИП, кредит на оборудование | Одобрено |
| `9900000063` | ООО «Старт Логистик» | молодая компания | Одобрено на других условиях |
| `9900000070` | ООО «Удача Плюс» | рисковый ОКВЭД, убыток | Отказ |
| `9900000088` | — | валидный ИНН без записи в реестре | Ошибка на шаге проверки ИНН (404) |

ИНН начинаются с `99`, чтобы подчеркнуть синтетику. Контрольная сумма рассчитана по алгоритму ФНС: 10 цифр для юрлица, 12 для ИП.

## Сценарий проверки для жюри (5–7 минут)

1. **Гость.** Откройте http://localhost:8080. Проверьте продукты, калькулятор и FAQ. Нажмите «Регистрация» или «Войти».
2. **Здоровый клиент.** Войдите как `client1` / `DemoPass123!` → «Новая заявка». Выберите «Оборотный кредит», цель «Пополнение оборотных средств». На шаге компании укажите `9900000017`, нажмите «Проверить», дождитесь карточки компании. Укажите сумму 3 000 000 ₽ и срок 24 мес. При желании приложите PDF. На последнем шаге отправьте заявку.
3. **Сотрудник.** Выйдите и войдите как `employee1`. Заявка обычно назначается ему (при занятости проверьте `employee2` и `employee3`) в разделе «Очередь заявок». Откройте карточку: изучите реестр, БКИ и прозрачный скоринг. Нажмите «Одобрить» и подтвердите решение.
4. **Результат.** Вернитесь как `client1` → «Мои заявки» → «Открыть решение». Примите оферту, нажмите «Подписать договор (демо)», затем «Получить средства (демо)». Появятся статусы «Оферта принята», «Договор подписан», «Средства перечислены».
5. **Другие условия.** Создайте заявку с ИНН `9900000031` на 8 000 000 ₽. После автоматических проверок сотрудник увидит рекомендацию «Одобрено на других условиях» с суммой около 4 000 000 ₽. Выберите действие «Другие условия» и подтвердите скорректированные параметры. Клиент увидит новую сумму.
6. **Отказ.** Создайте заявку с ИНН `9900000024` (активная просрочка). Автоматический слой зафиксирует стоп-фактор. Сотрудник выбирает «Отказать» и указывает понятную причину. Клиент видит отказ и может нажать «Подать заново».
7. **Нужны данные.** Создайте заявку с ИНН `9900000049` на 1 500 000 ₽. Заявка получит статус «Требуется уточнение». В решении укажите выручку `6000000` и прибыль `800000`, отправьте ответ. Проверки продолжатся автоматически, после чего заявку можно одобрить.
8. **Администратор.** Войдите как `admin`. Проверьте:
   - «Пользователи и роли» — смена роли клиента на сотрудника и обратно с подтверждением;
   - «Все заявки» — режим наблюдения, назначение сотрудника без права кредитного решения;
   - «Журнал аудита» — нажмите «Проверить целостность», откройте запись и хеши;
   - «Справочники» — изменение продукта и создание новой версии параметров скоринга.
9. **Права.** Убедитесь, что клиент не видит чужие заявки, сотрудник — незакреплённые и собственные заявки в служебном контуре, а администратор не может принять кредитное решение. Войдите сотрудником или администратором и проверьте блок «Кабинет предпринимателя»: продукты, новая заявка, мои заявки и профиль компании.

Полезные дополнительные сценарии: `9900000056` — ликвидированная компания, `9900000063` — молодая компания, `990000001246` — ИП и оборудование (обязателен залог), `9900000070` — рисковый ОКВЭД, `9900000088` — ошибка проверки ИНН.

## Автоматические проверки

1. **VALIDATION:** полнота полей, длина и контрольная сумма ИНН, лимиты продукта, цель, обеспечение.
2. **ENRICHMENT:** HTTP-запросы к локальным `registry-mock` и `bki-mock` с таймаутом и повторами. Сырые ответы сохраняются как снимок. При недоступности источник заявка переходит в `NEED_INFO` с понятным сообщением, а не теряется.
3. **SCORING:** 0–100, база 50, прозрачные факторы: возраст, сумма к выручке, прибыль, просрочки, долговая нагрузка, ОКВЭД, обеспечение. Параметры — версионируемая конфигурация в БД.
4. **DECISION_DRAFT:** отдельный слой кредитной логики. Стоп-факторы: недействующая компания, активная просрочка, требования продукта. Нет финансовых данных → `NEED_INFO`. Балл ≥ 70 → одобрено; 40–69 → другие условия; < 40 → отказ.
5. **IN_REVIEW:** автоматическое назначение по минимальной нагрузке и правилу «свежего взгляда». Финальное решение всегда принимает человек.

## Безопасность и надёжность

- RBAC и объектная авторизация на каждом эндпоинте; UI не является границей безопасности.
- Argon2id для паролей; JWT Bearer с ограниченным сроком; rate limit входа.
- Проверка MIME, расширения, сигнатуры и размера загружаемых файлов; приватный том.
- CORS из конфигурации, security-заголовки, CSP, request id в JSON-логах.
- Транзакции, Idempotency-Key при отправке заявки, индексы, миграции Alembic.
- Append-only аудит: запрет `UPDATE`/`DELETE` триггером PostgreSQL и SHA-256-цепочка с проверкой.
- Healthchecks, restart policy, старт только после готовности зависимостей.
- Внешние вызовы только к двум локальным мокам; платных сервисов и ключей нет.

## Тесты

Unit/API-тесты (SQLite, без Docker):

```bash
cd backend
python -m pytest
```

В контейнере:

```bash
docker compose exec backend python -m pytest
```

Покрыто: контрольная сумма ИНН, каждый фактор скоринга, кредитная логика и четыре исхода, допустимые/недопустимые переходы, объектные права, правило «свежего взгляда», обязательные комментарии, недоступность собственной заявки сотрудника в служебном контуре, клиентский кабинет для сотрудника и администратора, запрет одобрения для администратора, целостность цепочки аудита.

E2E на поднятом compose — все восемь сценариев, четыре исхода, идемпотентность, загрузка документа, оферта/подписание/зачисление, клиентский кабинет сотрудника и администратора, сокрытие собственной заявки сотрудника в служебном контуре и запрет кредитного решения для администратора:

```bash
sh scripts/e2e.sh
# или снаружи:
python scripts/e2e.py
```

Требуется `httpx` для запуска снаружи; внутри backend-контейнера он уже установлен. Полные сценарии: [docs/test-scenarios.md](docs/test-scenarios.md). Postman: [коллекция](docs/postman/CreditPath.postman_collection.json) и [окружение](docs/postman/CreditPath.postman_environment.json).

## Что вошло в MVP

- Полный путь клиента, автоматический конвейер, назначение, финальное решение сотрудника.
- Четыре исхода, ответ на запрос данных, оферта, демо-подписание и демо-зачисление.
- Четыре роли и серверная объектная авторизация; клиентский кабинет доступен всем авторизованным ролям, служебные действия — только по назначению.
- Три продукта, аннуитетный калькулятор, черновики, загрузка документов.
- Центр внутренних уведомлений, таймлайн, история, понятные ошибки и пустые состояния.
- Администрирование пользователей, ролей, продуктов, параметров скоринга; аудит с проверкой цепочки.
- Docker Compose с healthchecks, миграции, seed, unit-тесты и e2e.

## Что не вошло и почему

- Реальные кредитные, реестровые и БКИ-интеграции — ограничение кейса, используются локальные моки.
- Юридически значимая подпись и реальное зачисление — только имитация, явно помеченная.
- OCR документов, LLM-подбор, ИИ-подсказки сотруднику — не обязательны для сквозного сценария; вынесены в [ROADMAP](docs/ROADMAP.md).
- Внешние каналы оповещений, мобильное приложение и платные сервисы — запрещены условиями кейса.
- Production-контур: очередь фоновых задач, 2FA, несколько пользователей на компанию, промышленный мониторинг — в ROADMAP.

## Ограничения демо

- Фоновый конвейер выполняется внутри одного процесса backend; после перезапуска используется сохранённое состояние.
- Rate limit хранится в памяти процесса.
- JWT хранится в localStorage; для production нужна пара httpOnly refresh-cookie и короткий access-token.
- Все пользователи и компании вымышлены. Совпадения с реальными организациями случайны.
