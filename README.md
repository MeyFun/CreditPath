# CreditPath

Демонстрационный прототип цифрового кредитного кабинета для малого и микробизнеса. Один веб-продукт, в котором предприниматель выбирает продукт, проверяет компанию по ИНН, подаёт заявку и видит её статус, а сотрудник банка обрабатывает назначенную заявку и принимает финальное решение. Администратор управляет ролями и справочниками и читает неизменяемый журнал аудита.

> Все компании, ИНН, финансовые показатели, реестр и кредитная история — синтетические. Подписание договора и зачисление средств имитируются и явно помечены в интерфейсе. Прототип не является кредитной организацией и не предлагает реальные финансовые услуги.

## Сквозной сценарий

```text
Гость → каталог / калькулятор / FAQ
Клиент → потребность → продукт → проверка ИНН → черновик → полномочия и согласия → отправка
Система → VALIDATION → ENRICHMENT (registry + BKI) → SCORING → DECISION_DRAFT → IN_REVIEW
Сотрудник → одобрить / другие условия / запросить данные / отказать
Клиент → оферта → демо-подписание → демо-зачисление
Администратор → роли, справочники, все заявки, проверка цепочки аудита
```

Роли разделены как в крупном банке: **рабочая учётная запись сотрудника или администратора не действует как заявитель**, клиентский кабинет (`/api/client/*`) доступен только роли «Клиент». При этом:

- если клиент — связанное лицо сотрудника банка (сам сотрудник со своим бизнесом или родственник), его заявки никогда не назначаются этому сотруднику, а карточка заявки показывает отметку «Связанное лицо»;
- повторная заявка после отказа не попадает к сотруднику, который уже рассматривал цепочку («свежий взгляд»), а новый рецензент видит историю прошлых решений и причины;
- служебные разделы доступны только соответствующей роли: очередь и решения — сотруднику, управление ролями, справочниками и аудит — администратору; администратор не принимает кредитных решений.

## Стек

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2, PostgreSQL 16, pytest.
- **Frontend:** React 18, TypeScript, Vite, React Router, TanStack Query, собственная CSS-дизайн-система.
- **Runtime:** nginx отдаёт SPA и проксирует `/api`, `/docs`, `/openapi.json`, локальный Swagger UI.
- **Моки:** два независимых FastAPI-сервиса `registry-mock` и `bki-mock`.
- **Инфраструктура:** Docker Compose, healthchecks, именованные тома, non-root процессы.
- **Фиксация версий:** `frontend/package-lock.json`; `requirements.lock` у backend и обоих моков (все транзитивные версии, `uv pip compile` под Linux и Python 3.12), образы с точными тегами.

## Быстрый запуск

Требования: Docker Engine 24+ и Docker Compose v2, около 2 ГБ свободной памяти, свободные порты `8080`, `8000` и `55432` (последние два слушают только `127.0.0.1`).

```bash
docker compose up --build
```

Опционально можно заранее скопировать настройки:

```bash
cp .env.example .env
```

Без `.env` compose использует демонстрационные значения по умолчанию, поэтому команда выше запускается на чистом клоне. После старта:

| Что | Адрес |
|---|---|
| Веб-приложение | http://localhost:8080 |
| Swagger UI | http://localhost:8080/docs |
| OpenAPI JSON | http://localhost:8080/openapi.json |
| API напрямую | http://localhost:8000/api |
| Health backend | http://localhost:8000/health |
| PostgreSQL (только localhost) | `127.0.0.1:55432` |

Остановка и полный сброс данных:

```bash
docker compose down
docker compose down -v   # ВНИМАНИЕ: удаляет базу и загруженные файлы
```

## Где хранятся данные и как посмотреть базу

Все учётные записи, заявки, документы и аудит хранятся в PostgreSQL. Данные находятся в именованном Docker-томе `creditpath_postgres_data` и переживают обычный перезапуск контейнеров:

```bash
docker compose restart
docker compose down
docker compose up -d
```

**`docker compose down -v` удаляет том вместе со всеми зарегистрированными пользователями и заявками.** Эту команду нельзя использовать, если нужно сохранить данные.

Подключение к базе через `psql` внутри контейнера:

```bash
docker compose exec db psql -U creditpath -d creditpath
```

Полезные команды:

```sql
\dt
SELECT id, username, full_name, role, company_inn, created_at FROM users ORDER BY id;
SELECT id, public_number, status, scoring_score, final_outcome FROM applications ORDER BY id;
SELECT id, created_at, actor_label, action, entity_id FROM audit_log ORDER BY id DESC LIMIT 20;
```

Для графического клиента (DBeaver, pgAdmin, DataGrip):

| Параметр | Значение |
|---|---|
| Host | `127.0.0.1` |
| Port | `55432` |
| Database | `creditpath` |
| User | `creditpath` |
| Password | `creditpath_demo` |

Порт опубликован только на loopback-интерфейсе. Если значение `POSTGRES_HOST_PORT` занято, измените его в `.env`.

Резервная копия и восстановление:

```bash
docker compose exec -T db pg_dump --clean --if-exists -U creditpath -d creditpath > creditpath_backup.sql
docker compose cp creditpath_backup.sql db:/tmp/creditpath_backup.sql
docker compose exec db psql -U creditpath -d creditpath -f /tmp/creditpath_backup.sql
```

## Сценарий проверки для жюри (5–7 минут)

1. **Гость.** Откройте http://localhost:8080. Проверьте продукты, калькулятор и FAQ. Нажмите «Регистрация» или «Войти».
2. **Здоровый клиент.** Войдите как `client1` / `DemoPass123!`. → «Новая заявка». На шаге «Потребность» выберите «Пополнение оборотных средств», продукт подберётся сам. На шаге компании укажите `9900000017`, нажмите «Проверить». Укажите сумму 3 000 000 ₽ и срок 24 мес., при желании приложите PDF. На последнем шаге выберите должность, подтвердите полномочия и согласия на запрос в БКИ и обработку ПДн, отправьте заявку.
3. **Сотрудник.** Выйдите и войдите как `employee1`. Заявка обычно назначается ему (при занятости проверьте `employee2` и `employee3`) в разделе «Очередь заявок». Откройте карточку: изучите реестр, БКИ и прозрачный скоринг. Нажмите «Одобрить» и подтвердите решение.
4. **Результат.** Вернитесь как `client1` → «Мои заявки» → «Открыть решение». Статус обновляется сам, без перезагрузки. Примите оферту, нажмите «Подписать договор», затем «Получить средства». Появятся статусы «Оферта принята», «Договор подписан», «Средства перечислены».
5. **Другие условия.** Создайте заявку с ИНН `9900000031` на 8 000 000 ₽. После автоматических проверок сотрудник увидит рекомендацию «Одобрено на других условиях» с суммой около 4 000 000 ₽. Выберите действие «Другие условия»: можно изменить сумму, срок или предложить другой продукт. Клиент увидит новые условия.
6. **Отказ и «свежий взгляд».** Создайте заявку с ИНН `9900000024` (активная просрочка). Автоматический слой зафиксирует стоп-фактор. Сотрудник выбирает «Отказать» и указывает понятную причину. Клиент видит отказ и нажимает «Подать заново». Повторную заявку получает другой сотрудник: в карточке справа блок «Прошлые заявки клиента» с решением и причиной.
7. **Связанное лицо.** Войдите как `client3` и отправьте заявку на «Кредит на оборудование» (ИНН `990000001246`, с залогом). Заявку получит `employee1` или `employee2`, но не `employee3`; в карточке есть отметка «Связанное лицо сотрудника банка».
8. **Нужны данные.** Создайте заявку с ИНН `9900000049` на 1 500 000 ₽. Заявка получит статус «Требуется уточнение». В решении укажите выручку `6000000` и прибыль `800000`, отправьте ответ. Проверки продолжатся автоматически, после чего заявку можно одобрить.
9. **Администратор.** Войдите как `admin`. Проверьте:
   - «Пользователи и роли» — смена роли клиента на сотрудника и обратно с подтверждением;
   - «Все заявки» — режим наблюдения, назначение сотрудника без права кредитного решения;
   - «Журнал аудита» — нажмите «Проверить целостность», откройте запись и хеши;
   - «Справочники» — изменение продукта и создание новой версии параметров скоринга.
10. **Права.** Убедитесь, что клиент не видит чужие заявки, сотрудник не видит незакреплённые заявки и заявки связанных лиц, администратор не может принять кредитное решение, а у сотрудника и администратора нет клиентского кабинета.

Полезные дополнительные сценарии: `9900000056` — ликвидированная компания, `9900000063` — молодая компания, `990000001246` — ИП и оборудование (обязателен залог), `9900000070` — рисковый ОКВЭД, `9900000088` — ошибка проверки ИНН.

## Автоматические проверки

1. **VALIDATION:** полнота полей, длина и контрольная сумма ИНН, лимиты продукта, цель, обеспечение.
2. **ENRICHMENT:** HTTP-запросы к локальным `registry-mock` и `bki-mock` с таймаутом и повторами. Сырые ответы сохраняются как снимок. При недоступности источника заявка переходит в `NEED_INFO` с понятным сообщением, а не теряется.
3. **SCORING:** 0–100, база 50, прозрачные факторы: возраст, сумма к выручке, прибыль, просрочки, долговая нагрузка, ОКВЭД, обеспечение. Параметры — версионируемая конфигурация в БД.
4. **DECISION_DRAFT:** отдельный слой кредитной логики. Стоп-факторы: недействующая компания, активная просрочка, требования продукта. Нет финансовых данных → `NEED_INFO`. Балл ≥ 70 → одобрено; 40–69 → другие условия; < 40 → отказ.
5. **IN_REVIEW:** автоматическое назначение по минимальной нагрузке и правилу «свежего взгляда». Финальное решение всегда принимает человек.
6. **Риск-исключение:** если сотрудник одобряет заявку при скоринге ниже порога 70 или вопреки стоп-фактору/отказу системы, создаётся отдельное событие `application.risk_override` в аудите и в истории заявки. Интерфейс предупреждает сотрудника до принятия решения.

## Безопасность и надёжность

- RBAC и объектная авторизация на каждом эндпоинте; UI не является границей безопасности.
- Argon2id для паролей; JWT Bearer с ограниченным сроком; rate limit входа по IP+логину (5 попыток) и мягкий лимит по логину (20 попыток) против распределённого перебора.
- Адрес клиента берётся из соединения; `X-Forwarded-For` учитывается только от nginx (`FORWARDED_ALLOW_IPS`), API и БД опубликованы только на `127.0.0.1`.
- Мутации заявки блокируют строку (`SELECT … FOR UPDATE`): двойной клик не выполнит действие дважды.
- Клиент не получает внутренние данные: скоринг, черновик решения, назначения и риск-исключения отфильтрованы из истории заявки.
- При отправке заявки фиксируются должность заявителя, подтверждение полномочий и согласия на запрос в БКИ и обработку ПДн (история заявки и аудит).
- Проверка MIME, расширения, сигнатуры и размера загружаемых файлов; приватный том.
- CORS из конфигурации, security-заголовки, CSP, request id в JSON-логах.
- Транзакции, Idempotency-Key при отправке заявки, индексы, миграции Alembic.
- Append-only аудит: запрет `UPDATE`/`DELETE` триггером PostgreSQL и SHA-256-цепочка с проверкой.
- Healthchecks, restart policy, старт только после готовности зависимостей.
- Внешние вызовы только к двум локальным мокам; платных сервисов и ключей нет.

Unit/API-тесты (SQLite, без Docker):

```bash
cd backend

```

В контейнере:


Покрыто: контрольная сумма ИНН, каждый фактор скоринга, кредитная логика и четыре исхода, лимит к выручке при высоком балле, допустимые/недопустимые переходы, объектные права, правило «свежего взгляда» и история прошлых решений, связанное лицо, отсутствие клиентского кабинета у сотрудника и администратора, запрет одобрения для администратора, «другие условия» с другим продуктом, фильтрация внутренних событий для клиента, полномочия и согласия при отправке, исправление ИНН в ответе на запрос, rate limit входа, целостность цепочки аудита.

E2E на поднятом compose — все восемь сценариев, четыре исхода, идемпотентность, загрузка документа, оферта/подписание/зачисление, запрет кредитного решения для администратора, закрытый клиентский кабинет у сотрудника и администратора и правило связанного лица:

```bash
sh scripts/e2e.sh
# или снаружи:
python scripts/e2e.py
```

Требуется `httpx` для запуска снаружи; внутри backend-контейнера он уже установлен. Полные сценарии: [docs/test-scenarios.md](docs/test-scenarios.md). Postman: [коллекция](docs/postman/CreditPath.postman_collection.json) и [окружение](docs/postman/CreditPath.postman_environment.json).

## Что вошло в MVP

- Полный путь клиента, автоматический конвейер, назначение, финальное решение сотрудника.
- Четыре исхода, ответ на запрос данных, оферта, демо-подписание и демо-зачисление.
- Четыре роли и серверная объектная авторизация; рабочие и клиентские учётки разделены, связанные лица исключены из назначения.
- Шаг «на что нужны деньги» с автоподбором продукта; полномочия и согласия при отправке.
- Три продукта, аннуитетный калькулятор, черновики, загрузка документов.
- Центр внутренних уведомлений, таймлайн, история, понятные ошибки и пустые состояния.
- Администрирование пользователей, ролей, продуктов, параметров скоринга; аудит с проверкой цепочки.
- Docker Compose с healthchecks, миграции, seed, unit-тесты и e2e.

## Что не вошло и почему

- Реальные кредитные, реестровые и БКИ-интеграции — ограничение кейса, используются локальные моки.
- Юридически значимая подпись и реальное зачисление — только имитация, явно помеченная.
- ИИ-ассистент, OCR документов и ИИ-подсказки сотруднику — по ТЗ ИИ приветствуется, но не обязателен; план (открытая модель в отдельном контейнере, правила как резерв) — в [ROADMAP](docs/ROADMAP.md).
- Внешние каналы оповещений, мобильное приложение и платные сервисы — запрещены условиями кейса.
- Production-контур: очередь фоновых задач, 2FA, несколько пользователей на компанию, промышленный мониторинг — в ROADMAP.

## Ограничения демо

- Фоновый конвейер выполняется внутри одного процесса backend; после перезапуска используется сохранённое состояние.
- Rate limit хранится в памяти процесса.
- JWT хранится в localStorage; для production нужна пара httpOnly refresh-cookie и короткий access-token.
- Все пользователи и компании вымышлены. Совпадения с реальными организациями случайны.
